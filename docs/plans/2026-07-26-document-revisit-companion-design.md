# 文档回访伙伴：浏览器扩展测试版设计

状态：已确认，待用户审核书面规格
日期：2026-07-26

## 1. 产品定义

文档回访伙伴是覆盖 Notion、ima、飞书网页版及普通网页文档的轻量浏览器扩展。

用户学完或读完当前文档后，通过快捷键呼出宠物并 Mark。第一次 Mark 代表用户今天已经完成了一次学习，因此立即获得 25% 进度。宠物随后按 1 / 2 / 7 / 30 节奏，把原文档带回给用户。每完成一次回访，文档增加 25%；第四次完成后进入“已经长成”状态。

产品不建立新的知识库，不复制、解析或总结文档正文，只保存原文档指针和回访状态。

## 2. 目标用户与核心任务

目标用户是经常记录、收藏和制定学习计划，但容易因为想得太多、计划太大而迟迟不开始的人。

核心任务：

> 让用户在读完一份文档后，5 秒内确认“今天已经做了”，立即获得可见进度，并在未来三次低压力回访中再次遇见它。

测试版的核心成功体验是：

1. 第一次行动立即获得 25%，而不是创建一笔未来待偿还的任务。
2. 宠物庆祝“愿意开始和回来”，不评判用户是否真正掌握。
3. 错过回访不会扣分、清零或制造积压焦虑。

## 3. 设计原则

- **先给完成感**：第一次 Mark 即完成第一阶段。
- **一次只看一份**：不展示积压墙或逾期总数。
- **原文留在原处**：回访时跳回 Notion、ima、飞书或原网页。
- **不考试**：测试版不要求答题、摘要或自评难度。
- **不惩罚中断**：进度永不因延迟清零。
- **少权限、默认本地**：只在用户主动操作时读取当前标签页标题和 URL。
- **表现与逻辑分离**：不同宠物皮肤共享相同的四阶段进度。

## 4. 核心工作流

### 4.1 第一次 Mark

1. 用户在任意网页文档中按扩展快捷键或点击工具栏图标。
2. 浏览器原生侧边栏打开。
3. 扩展读取当前标签页标题、URL 和来源域名。
4. 未 Mark 的文档显示主操作：`今天见过了 · 收下 25%`。
5. 用户点击后：
   - 创建文档记录；
   - 将阶段设置为 1；
   - 记录第一次完成时间；
   - 安排下一次回访；
   - 播放一次宠物成长动画；
   - 显示温和确认文案。

不要求用户分类、打标签、写摘要或选择提醒日期。

### 4.2 等待回访

已 Mark 但未到期的文档显示：

- 当前进度：25%、50% 或 75%；
- 下次见面日期；
- 打开原文档；
- 删除记录。

同一天不能通过重复点击连续推进阶段。

### 4.3 到期回访

1. 到期时，扩展工具栏图标显示一个小圆点，不显示数量。
2. 用户点击带圆点的工具栏图标后进入回访模式；快捷键始终进入当前文档模式。
3. 回访模式中，宠物一次只带回一份到期文档。
4. 多份文档同时到期时，先选择 `nextReviewAt` 最早的文档；时间相同时选择最早创建的文档。
5. 用户点击卡片，在原标签页或新标签页打开原文档。
6. 用户看完后点击 `这次看完了`。
7. 扩展记录本次完成时间、增加 25% 并安排下一次回访。
8. 如果还有其他到期文档，完成当前文档后才显示下一份；界面仍不显示剩余数量。

### 4.4 已经长成

第四次完成后：

- 文档进度为 100%；
- 播放完整成长动画；
- 文档进入“已经长成”列表；
- 不再自动提醒；
- 保留打开原文档和删除记录的能力。

## 5. 1 / 2 / 7 / 30 调度语义

正常节奏对应第 1、2、7、30 天。实现使用阶段间隔：

- 第一次 Mark 后：1 天；
- 第二次完成后：5 天；
- 第三次完成后：23 天；
- 第四次完成后：结束。

如果用户延迟回访，后续间隔从实际完成时间重新计算。这样不会在用户补完一次后立刻出现下一个已经逾期的阶段，也不会形成回访债务。

阶段推进必须满足：

- 当前阶段已到期；
- 本阶段尚未完成；
- 同一操作不能重复写入；
- 阶段最大值为 4。

## 6. 宠物与皮肤

每个用户拥有一只常驻宠物，陪伴所有文档。

每份文档单独保存四阶段进度；宠物根据当前展示文档的阶段播放对应状态。皮肤只负责把 25%、50%、75%、100% 映射为不同视觉表现，不改变调度规则。

测试版只实现一款“流体充盈”皮肤：

- 25%：首次充盈，立即出现可见变化；
- 50%：身体色彩达到一半，表情更活跃；
- 75%：接近完整，出现轻量光效；
- 100%：完全充盈并播放庆祝动画。

数据结构保留 `skinId`，但测试版不实现皮肤商城、解锁规则或编辑器。

## 7. 界面状态

浏览器侧边栏只有四种主状态：

1. **未 Mark**：当前文档标题、来源和第一次 Mark 按钮。
2. **等待回访**：进度、下次日期、打开原文和删除。
3. **到期回访**：单份回访卡、打开原文、完成回访。
4. **已经长成**：100% 状态和完成收藏。

首次打开但无法读取有效网页时，显示简短说明，不创建空记录。

入口规则：

- 快捷键：打开当前文档状态，保证 Mark 动作不被其他到期记录打断。
- 工具栏图标：有到期文档时打开回访状态；没有到期文档时打开当前文档状态。

## 8. 技术架构

测试版是 Manifest V3 Chromium 浏览器扩展。

### 8.1 扩展组件

- **Side Panel**：承载宠物、当前文档和回访卡。
- **Service Worker**：处理快捷键、调度检查、阶段推进和徽标状态。
- **Commands API**：注册可由用户修改的快捷键。
- **Active Tab**：仅在用户主动呼出扩展时读取当前标签页标题和 URL。
- **Storage API**：保存文档、设置和宠物皮肤。
- **Alarms API**：定期检查是否有到期文档。

测试版不需要内容脚本，不读取页面正文，也不申请覆盖所有网站的 host permissions。

Service Worker 在浏览器启动时检查一次到期状态，并使用每 60 分钟一次的 alarm 更新工具栏圆点。测试版不申请系统通知权限，不发送操作系统弹窗。

### 8.2 本地优先

数据使用 `chrome.storage.local`。不实现登录、云端数据库或自建同步服务。

浏览器同步、账号体系和跨设备状态只有在本地测试验证回访价值后才评估。

## 9. 数据模型

```ts
type ReviewStage = 1 | 2 | 3 | 4

type DocumentRecord = {
  id: string
  title: string
  url: string
  normalizedUrl: string
  source: string
  stage: ReviewStage
  completedAt: string[]
  nextReviewAt: string | null
  createdAt: string
  updatedAt: string
}

type CompanionSettings = {
  skinId: 'fluid-default'
  reducedMotion: boolean
}
```

`normalizedUrl` 是测试版的去重键。规范化只移除 URL fragment，并保留可能决定文档身份的 query 参数。相同规范化 URL 再次呼出扩展时打开已有记录，不创建重复项。

## 10. 异常与恢复

- **标题缺失**：使用域名和 Mark 时间生成回退标题。
- **重复 Mark**：打开已有记录。
- **浏览器未运行**：下次启动后重新计算到期状态。
- **错过日期**：文档保持当前进度；不清零、不叠加多个逾期阶段。
- **原链接失效**：允许修改 URL 或删除记录，已有进度保持不变。
- **存储失败**：不播放成功动画，显示可重试提示。
- **多次点击**：阶段推进操作必须幂等，避免一次操作增加多个阶段。
- **扩展卸载**：本地数据会随扩展卸载清除；测试版不承诺云端恢复。

## 11. 可访问性

- 所有操作支持键盘完成。
- 进度同时使用数字和文字，不只依赖颜色。
- 尊重系统 `prefers-reduced-motion`，并提供扩展内减少动态效果设置。
- 动画不会阻挡主操作或导致内容闪烁。
- 按钮提供明确的可访问名称和焦点状态。

## 12. 测试与验收

### 12.1 最小自动检查

为纯调度函数保留一个可运行测试，覆盖：

- 正常按时完成四阶段；
- 延迟后从实际完成时间顺延；
- 重复点击不重复推进；
- 第四阶段后不再产生回访日期。

### 12.2 手工冒烟测试

在 Notion 作为主测试环境，同时抽查 ima 和飞书网页版：

1. 任意文档可在 5 秒内完成 Mark。
2. 第一次 Mark 立即显示 25% 和宠物动画。
3. 浏览器重启后记录、日期和皮肤状态仍存在。
4. 相同 URL 不会产生重复记录。
5. 到期时只显示小圆点和一份文档。
6. 点击卡片能回到原文档。
7. 四次完成后准确进入 100%。
8. 减少动态效果设置生效。

## 13. 测试版不做

- 文档正文读取、复制、快照或全文存储；
- AI 总结、问答、知识图谱或闪卡；
- Notion、ima、飞书专用 API 集成；
- Obsidian 桌面插件；
- 登录、云同步和后端服务；
- 自定义复习算法、FSRS 或难度评分；
- 逾期计数、连续打卡、排行榜或惩罚；
- 多皮肤实现、商城、货币或装扮系统；
- 系统级桌面悬浮窗和移动端应用。

## 14. 后续验证

测试版只回答三个问题：

1. 用户是否愿意在读完文档后主动 Mark？
2. 立即获得 25% 是否真的增强“我已经开始”的满足感？
3. 宠物带回原文档的方式，是否比传统提醒更愿意让用户再次打开？

只有这三个问题得到正向结果后，再考虑多皮肤、跨设备同步、Obsidian 适配和更智能的回访节奏。
