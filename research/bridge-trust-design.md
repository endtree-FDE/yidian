# 双端可信通道 · 调研与设计（扩展 ↔ 桌面端）

日期：2026-11-14
状态：已实现并验收（配对 + token + 装完即对齐；见 §6 验收）。
背景：桌面端成了主产品后，扩展与桌面端之间那条本地通道就成了新的信任边界。

## 0. 出发点：原来的门基本等于没有

上一轮加的本地桥，鉴权逻辑是：

```js
function isAllowedOrigin(origin) {
  if (!origin) return true;                    // 没有 Origin 就放行
  return origin.startsWith('chrome-extension://')
    || origin.startsWith('app://')
    || origin.startsWith('http://127.0.0.1')
    || origin.startsWith('http://localhost');
}
```

配合 `access-control-allow-origin: origin`（原样回显被放行的来源），实际效果是：

| 谁能碰到你的收藏 | 原来 | 现在 |
|---|---|---|
| 本机任意进程（curl / node） | 能读能写 | **不能**（业务端点要 token） |
| 本机任何 web 服务里的页面 | 能跨域读走 | **不能**（Origin 不是扩展就拒） |
| 浏览器里别的扩展 | 能读能写 | **不能**（要配对 + token） |
| 没带 token 的网页脚本 | 能写 | **不能** |

收藏里是标题、URL、选段——等于你的阅读轨迹。这不是理论风险，是几行代码的事。

## 1. 能抄的架构（成熟案例怎么做）

### 1.1 Chrome Native Messaging（官方机制）

扩展与本机应用通信的**官方**通道：扩展声明 `nativeMessaging` 权限，本机装一个 native host（可执行文件 + 一份 host manifest），浏览器负责拉起它、用 stdio 传消息。

- host manifest 里 `allowed_origins` 写死扩展 ID —— **只有那个扩展能连上**。
- 注册位置分浏览器：Windows 注册在
  `HKCU\Software\Google\Chrome\NativeMessagingHosts\<name>`（Edge 是 `…\Microsoft\Edge\…`），
  macOS 是 `/Library/Google/Chrome/NativeMessagingHosts/*.json`。
- 浏览器是**中介**：本机进程碰不到这条通道，冒充不了扩展。

**我们抄的部分**：扩展 ID 白名单 + 「浏览器做中介」的思路。
**我们没抄的部分**：native host 的注册与 stdio 协议（见 §3）。

### 1.2 mcp-chrome（真实开源的「扩展 + 本机服务」）

它的本机服务把安全写成三条明规则：**只连 127.0.0.1**、**硬编码扩展 ID 白名单**、**每次连接都校验**（不信任「请求看起来像扩展」）。

**我们抄的部分**：逐请求校验身份 + 明确的扩展 ID 白名单。

### 1.3 arXiv 2611.04291（NativeMessaging 的实证安全分析）

这篇实测研究的结论对我们最有用：**NativeMessaging 本身没有信任根**，恶意本机程序可以冒充扩展发起通信；作者建议的缓解是「**带外共享密钥 + 消息加密**」。

**我们抄的部分**：配对码就是那个「带外共享的密钥」——它通过屏幕传递，不经过通道。

### 1.4 KDE Connect / LocalSend / Syncthing（配对 UX）

- **KDE Connect**：两台设备互相看到后，要**双方确认**才建立信任；有配对码/二维码。
- **LocalSend**：局域网上「快速保存」需要设备配对，接收端要确认。
- **Syncthing**：设备 ID + 显式「接受这台设备」。

共同点：**信任不是自动的，要用户参与一次**；而且确认是**有时效**的一次性动作。

**我们抄的部分**：一次性 6 位码、5 分钟有效、只能用一次、猜错 5 次作废。

## 2. 产品洞察（不只是安全）

1. **「第一次连上」必须是一次动作，而不是一种状态。**
   用户装好桌面端后如果发现收藏是空的，他会以为产品坏了。让这件事需要一个**明确的、看得见的动作**（托盘里点一下、看到一串码、贴过去），反而是可信的信号。

2. **桌面端在跑但还没连上，是两种完全不同的状态，UI 要分开说。**
   我们的收藏库页现在会区分「桌面端未连接」（没装/没开）和「桌面端在运行，还没连上」（装了、在跑、差一次配对）——后者给具体指引，前者给安装指引。

3. **配对码要能复制，不要让人手抄。**
   桌面端生成码的同时写进剪贴板，用户在扩展里 `Ctrl+V`。手抄 6 位数字的失败率高得离谱。

4. **「已连接」之后就不该再打扰用户。**
   配好之后没有开关、没有红点、没有横幅。托盘里留一个「断开浏览器扩展」就够了。

5. **心跳要幂等。**
   装完桌面端后，扩展里攒的收藏要自动过去。我们让扩展**每个心跳推一次**自己的状态，桌面端用指纹判重后不重复写盘——「一分钟内自动对齐」，用户什么都不用做。

## 3. 明确不抄的（以及为什么）

| 不抄 | 原因 |
|---|---|
| **完整 Native Messaging** | 要在 Windows 注册表注册 native host（还得写 Edge 那条路径）、native host 进程要单独实现 stdio 协议（4 字节长度前缀），Electron 当 native host 还会撞单实例锁。代价远大于收益——而我们真正的收益点是「用户数据不被本机随手进程读写」，用带外配对码 + token 已经拿到大头。**记为演进路径，不是错误。** |
| **自动信任首个扩展** | 少一次操作，但等于把「谁在连」的决定权交给网络可达性。配对是一次性成本，长期收益更重要。 |
| **把 token 做成长期可读文件给扩展** | 扩展读不到本机文件，只能靠自己存储。token 落在扩展自己的 `chrome.storage.local`（别的扩展读不到，网页更读不到）✓ |
| **二维码配对** | LocalSend 的二维码要在手机场景才好用；这里是「同一台机器的另一个窗口」，6 位数字更快。 |
| **设备级信任链 / 多设备** | v1 只有一机一扩展。跨设备需要账号与后端，与「本地优先」有张力，另议。 |

## 4. 我们采用的模型

```
扩展（浏览器）                          桌面端（Electron）
┌────────────────────┐                ┌────────────────────────┐
│ 收藏库页            │                │ 托盘「连接浏览器扩展」  │
│  ┌──────────────┐  │  ① 用户把码   │  → 生成 6 位码（复制）   │
│  │ 输入配对码   │  │───贴过去────→ │  → 弹配对窗显示码        │
│  └──────────────┘  │                └────────────────────────┘
│        │            │                          │
│        │ ② POST /pair { code }                │
│        └───────────→│  ③ 校验码（一次性/限时/限次）│
│                     │  ④ 发 token，记下扩展 ID     │
│  ⑤ 存 token        │                          │
│  ⑥ POST /records ──→│  ⑦ mergeByKey 合并（新的赢） │
│     （带 token）    │  ⑧ 指纹没变就不写盘          │
└────────────────────┘                └────────────────────────┘
```

**协议**（两端共用一份，放在 `packages/yidian-core/bridge-protocol.mjs`）：

| 端点 | 需要什么 | 回什么 |
|---|---|---|
| `GET /ping` | 身份头 | `{ app, version, protocol, paired, pairingOpen }`，**不碰收藏** |
| `POST /pair` | 身份头 + 一次性码 | `{ ok, token }` |
| `GET /state` | 身份头 + token | 全量状态 |
| `POST /records` | 身份头 + token | 合并后的全量状态 |
| `POST /events` | 身份头 + token | 处理结果 + 全量状态 |

**身份怎么认（踩过坑的那一条）**：扩展发起的**简单 GET 不带 Origin 头**——Chromium 只在非简单请求上补 Origin。所以：

- 身份靠我们自己带的头 `x-yidian-extension`；
- Origin 有就必须是 `chrome-extension://`，且**要和身份头对得上**；
- 业务端点还要 `x-yidian-token`。

> 这个坑只有真实浏览器能暴露：Node 的 fetch 会自己带 Origin，单元测试全绿；等真扩展去探活时，桌面端会把「没带 Origin」的请求当成本机进程拒掉，扩展根本发现不了桌面端。

## 5. 残余风险（说清楚，别装看不见）

| 风险 | 现状 | 彻底解决要 |
|---|---|---|
| 同用户的恶意进程能读 `%APPDATA%/一点/store.json`（token 也在那儿） | 挡不住 | Native Messaging（浏览器做中介）或系统级凭据存储 |
| 扩展 ID 头可被本机进程伪造 | 挡不住（HTTP 的固有属性） | 同上 |
| 配对码被看见（肩窥 / 屏幕录制） | 5 分钟有效 + 一次性 | 缩短有效期 |
| 本机桥没有 TLS | 只绑 127.0.0.1 | 只绑回环即可，TLS 无必要 |

## 6. 验收（这一轮的量化目标）

1. **未配对来源一律读写不到**：本机进程（无 Origin 无身份头）、网页（`https://` Origin）、
   本机 web 服务（`http://127.0.0.1` Origin）、别的扩展 → 403，且响应体里没有收藏。
2. **配对要用户参与一次**：桌面端不发起配对时 `/pair` 返回 409；码错 401；过期 410；猜错 5 次 429。
3. **配对后 ≤1 分钟自动对齐**：扩展每个心跳推一次自己的状态，桌面端合并后指纹没变就不写盘。
4. **桌面端缺席 / 未配对时扩展行为零变化**：单测 46 项 + 扩展 e2e 3 项全绿。
5. **端到端**：真 Electron + 真 Chromium 联调，配对一次后桌面端存储里立刻出现扩展那条收藏。
